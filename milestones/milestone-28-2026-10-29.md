## 4. BIP-322 delegated authorization mechanism

**Reuse.** The verifier imports, unchanged, `verifyBip322P2TR` and
`p2trScriptPubKey` from `experiments/experiment-1/resolvers/resolver-js.mjs`.
Tests also use `controllerForSecret` and `signBip322` from
`experiments/experiment-1/tests/test-support.mjs`. No existing file was modified.

**Grant message.** Domain-separated, exactly two lines, no `\r`, no trailing
newline, fixed key order rebuilt by `canonicalGrantPayload()`:

```text
BITMAPVERSE DELEGATED PERMISSIONS / BUILD GRANT / v0.1
{"schema":"bitmapverse.permission.grant.v0.1","district":"937336.bitmap",
 "district_inscription_id":"…","authority_snapshot":{"height":…,"block_hash":"…"},
 "grantor":{"address":"bc1p…","script_pubkey":"5120…"},
 "grantee":{"address":"bc1p…","script_pubkey":"5120…"},
 "action":"build","object_id":"…","expires_at_height":…,"nonce":"…"}
```

(Shown wrapped; the signed payload is one line.)

- One BIP-322 Simple signature, by the grantor.
- `permission_id = SHA-256(exact UTF-8 message bytes)`; this is the revocation key.
- The domain prefix differs from Experiments #1, #22 and #25, so their
  signatures cannot be replayed as grants, and grant signatures cannot be
  replayed as Name bindings.

**Decision order (fail closed).** Each step returns `DENY` with a distinct code:

1. Grant absent → `NO_PERMISSION`
2. Request or grant shape, domain, schema or non-canonical bytes → `INVALID_REQUEST` / `MESSAGE_MISMATCH`
3. District, inscription, action, object or builder differ from the request → `WRONG_SCOPE`
4. `evaluation_height` before snapshot → `NOT_YET_VALID`; at or after `expires_at_height` → `EXPIRED`
5. Revocation state missing → `REVOCATION_STATE_UNAVAILABLE`; malformed → `REVOCATION_STATE_INVALID`; listed → `REVOKED`
6. Ownership evidence missing, malformed, not labelled `TEST_KEY_FIXTURE`, not at
   the exact `evaluation_height`, unconfirmed, spent, or holder ≠ grantor →
   `OWNERSHIP_*` / `UNSUPPORTED_EVIDENCE_SOURCE`
7. Signature not valid for the grantor → `INVALID_SIGNATURE`
8. Otherwise `ALLOW` / `DELEGATED_BUILD_PERMITTED`

No clock is read. Expiry is evaluated against the explicit `evaluation_height`.

## 5. Separation of ownership, authorization and rendering

| Concept | How it is kept separate |
| --- | --- |
| Signature validity | Checked by `verifyBip322P2TR` only. A valid signature alone never yields `ALLOW`. |
| District ownership | Checked separately against ownership evidence: grantor must be the District holder at the evaluation height. If the District is transferred, grants from the previous holder stop being valid. |
| Delegated permission | Grant + scope + expiry + revocation. Ownership is never transferred to the builder. |
| Rendering | `object_id` is opaque. It is not a renderer, 3D scene or portal reference. No renderer code is involved. |
| Name bindings | Not referenced by the grant and not modified. |

## 8. Safety and fail-closed conditions

Verified by four additional tests:

- Missing revocation state → `DENY REVOCATION_STATE_UNAVAILABLE`.
- Seven malformed revocation states (wrong type, extra key, wrong schema, wrong
  District, uppercase hex, unsorted, duplicate) → `DENY REVOCATION_STATE_INVALID`.
- Ownership evidence at a height other than `evaluation_height` →
  `DENY OWNERSHIP_HEIGHT_MISMATCH`.
- Evidence not labelled `TEST_KEY_FIXTURE` (for example `LIVE`) →
  `DENY UNSUPPORTED_EVIDENCE_SOURCE`. Fixture ownership is never presented as
  live ownership.

Every result, `ALLOW` and `DENY`, carries `authority_mode: "TEST_KEY_FIXTURE"`
and `revocation: "LOCAL_ONLY"`.

## 10. Explicit limitations

- **TEST_KEY_FIXTURE:** grants are signed with deterministic test keys, not by
  the real District holder. District ownership is simulated by fixture
  evidence at a synthetic height.
- **LOCAL_ONLY:** revocation is an explicit local input. It is not
  interoperable and not on-chain.
- **No verified live District ownership.** The verifier refuses live evidence
  by design in this milestone.
- **No builder-signed action authentication.** `ALLOW` proves that a valid,
  unexpired, unrevoked grant exists for the builder, object and District at the
  evaluation height. It does not prove who sent the request.
- **No rendering or portal integration.**
- **No Name-binding changes.**
- **No rent, payment, collateral or economic settlement.**

This milestone is not a production-ready permission system.

## 11. Remaining open questions

- Whether and how the real District holder signs a grant, and the custody path
  for that signature.
- Whether to add a live-evidence mode (for example reusing
  `resolveIndependentOwnership` from Experiment #24 unchanged) under a distinct
  `authority_mode`.
- How a builder authenticates a build action (a builder-signed request bound to
  `permission_id`).
- Whether revocation should become signed (for example following the
  Experiment #1 hash-chained `REVOKE` pattern), and how it would be discovered
  and shared beyond one local verifier.
- Where grants and revocations are published, and who may rely on them.
- A canonical object-identifier namespace that stays separate from rendering.
